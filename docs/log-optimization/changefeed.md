# Changefeed 场景：海量 changefeed 生命周期日志

## 背景

changefeed 生命周期会跨 `coordinator`、`operator`、`maintainer`、`dispatcher orchestrator` 等多个模块流转。创建、恢复、迁移、停止、移除、错误重试这些动作都会在不同位置留下日志。

changefeed 场景的治理重点是解决如下问题：

- 生命周期日志在多处重复打印。
- 默认日志里存在大量过程旁白和无意义文案。
- 一些日志带大对象和冗余字段，单条成本高、阅读成本也高。
- 长时间无进展时，默认日志缺少稳定的检测与提示。

## 当前存在的问题

### 1. 同一生命周期事件在多处重复打印

当前 changefeed 生命周期日志分散在多个模块中，单个动作很容易在不同层次重复表达。典型例子包括：

- `send command to maintainer`
- `maintainer received bootstrap response`
- `handle bootstrap response`
- `wait for stop changefeed operator finished`

这些日志会围绕同一条生命周期链路反复出现，最后形成的问题是：

- 同一件事在多个模块里重复说。
- 读者需要自己判断哪一条更接近根因，哪一条只是中间层转述。
- 默认日志量随生命周期推进不断增加。

### 2. 过程旁白多，真正有诊断价值的信息少

不少 changefeed 日志表达的是“刚刚执行了一步动作”或“还在继续等待”，但没有提供足够强的诊断信息。

这类日志的典型问题是：

- 只能看出流程走到了哪一步。
- 看不出为什么会停在这里。
- 看不出影响范围和下一步动作。

在默认 `INFO/WARN` 里保留这类过程旁白，会让日志数量变多，但对排障帮助有限。

### 3. 部分日志带大对象和冗余字段

当前 changefeed 场景里，一些日志会输出体积较大的对象或冗余上下文，例如：

- `info.String()`
- `status` 全量字符串
- `allNodesResp`
- `meta`

这类日志的问题比较直接：

- 单条日志成本高。
- 默认日志体积大，检索和阅读都更慢。
- 关键信息被淹没在大对象内容里。

### 4. 长时间无进展时，默认日志缺少稳定提示

changefeed 的 create、bootstrap、move、stop、remove、error retry 都可能进入长时间等待或无进展状态。

当前缺少一套稳定的检测方式，去回答下面这些问题：

- 哪个 changefeed 长时间没有推进。
- 它卡在生命周期的哪个环节。
- 这种卡住是局部个案，还是一批 changefeed 的共同问题。

这会导致两种结果：

- 正常路径日志很多，但异常停滞时仍然不够清楚。
- 值班同学只能从大量过程日志里反推“这个 changefeed 好像卡住了”。

## 解决思路

### 1. 围绕生命周期收敛日志，只保留关键状态切换和关键异常

changefeed 场景的默认日志应围绕生命周期结论来设计。适合保留在默认级别的，主要包括：

- 关键状态切换。
- 关键异常。
- 生命周期长时间无进展的 stalled 日志。

create、resume、move、stop、remove、error retry 这些动作里的大量中间步骤，不需要继续按步打印默认日志。

### 2. 删除无意义日志和重复表达

对 changefeed 生命周期日志，优先做下面两类清理：

- 删除只是在描述过程推进的旁白日志。
- 删除同一事件在多个层级上的重复表达。

治理后的目标是：

- 一件事尽量只在最合适的位置表达一次。
- 默认日志重点表达结论、异常和影响。
- 中间层不再反复转述同一生命周期动作。

### 3. 收缩字段，只保留对象、原因、动作、影响

changefeed 默认日志里的字段应聚焦少量高价值信息，例如：

- `changefeedID`
- 当前生命周期动作
- 当前状态或关键阶段
- 触发原因
- 系统动作
- 影响范围

字段收敛后，默认日志更容易做到：

- 一眼看出是哪一个 changefeed。
- 一眼看出发生了什么。
- 一眼看出为什么发生，以及系统接下来做什么。

### 4. 禁止默认日志输出大对象

默认 `INFO/WARN` 不应继续输出大对象、长字符串和大列表。

如果确实需要这类信息，应改成：

- 少量摘要字段。
- 代表性样本。
- 调试日志或局部诊断开关。

这样可以直接降低默认日志的单条体积，也能避免读者在大对象里手动提炼重点。

### 5. 对长时间无进展的 changefeed 增加检测机制

changefeed 场景需要一套独立的无进展检测机制，用来发现生命周期卡住的对象。

这套机制的目标是：

- 判断一个 changefeed 是否在预期时间内持续没有推进。
- 在确认长时间无进展后，输出少量 stalled 日志。
- 帮助值班同学快速定位“哪个 changefeed 卡住了、卡在什么环节”。

这样，默认日志可以在正常路径上保持收敛，同时保留对卡住场景的观测能力。

## 为什么这个思路可以解决问题

### 1. 它直接针对 changefeed 场景的主要问题

changefeed 场景当前最突出的矛盾是重复表达、过程旁白、冗余字段和大对象输出。

围绕生命周期收敛日志、删除重复表达、收缩字段之后，默认日志会直接变得更短、更聚焦，也更容易读懂。

### 2. 它更贴近 changefeed 场景的排障方式

changefeed 排障时，大家真正关心的是：

- 生命周期是否推进到了关键结论。
- 是否遇到了明确异常。
- 是否长时间卡在某个环节。

围绕这几个问题设计日志，比保留大量过程日志更符合实际排障需求。

### 3. 它能够同时降低日志量和提升日志质量

删除无意义日志、重复表达和大对象输出，会直接降低默认日志总量。

保留关键状态切换、关键异常和 stalled 检测日志，会提升默认日志的语义密度和诊断价值。

这两件事可以同时成立，不需要二选一。

### 4. 它补上了“静默之后如何发现异常”的缺口

生命周期日志收敛后，正常路径会更安静。长时间无进展的检测机制负责补上这一块：

- 正常推进时不刷屏。
- 真的卡住时能及时发声。

这样可以避免两种极端：

- 为了怕漏问题，保留大量过程日志。
- 为了降噪过度静默，结果卡住时没有稳定提示。
