# 治理原则与日志契约

## 目标

TiCDC 建立日志治理体系的目的，不是增加一套写日志的形式要求，而是长期提升默认日志的质量和使用效率。我们希望通过这套治理，达到下面几个结果：

- 提升日志质量，让默认 `INFO/WARN` 保留真正有诊断价值的信息。
- 提升日志协助排查问题的效率，让值班同学、开发者和 AI agent 能更快定位对象、原因、影响和下一步动作。
- 减少默认日志数量，清理控制流旁白、重复表达和低信息量日志，避免淹没真正有价值的日志。
- 避免对象规模扩大后的日志洪流，让系统在大规模场景下仍保持可读、可检索、可聚合。
- 让日志同时对人、AI agent 和 Loki 等日志平台友好，为后续检索、聚合和告警提供稳定基础。

## 日志的职责

日志的职责是：在系统运行中留下足够高价值的事实，帮助人和工具理解当前状态，并在未知问题发生时定位原因、影响和下一步动作。**打日志不是为了证明“代码走到了这里”，也不是为了给正常路径做逐步旁白。**


### 面向 AI 和 Loki 的消费要求

| 消费方 | 要求 |
| --- | --- |
| AI agent | 可解析：字段稳定；可归因：能直接看出对象、原因、动作和影响；可关联：能通过 `requestID`、`traceID`、`epoch` 等字段串起事件链；可摘要：高频事件默认有窗口摘要 |
| Loki 一类平台 | 可提取：低基数字段稳定；可检索：关键语义不能只藏在长 `message` 里；可聚合：高频事件通过窗口摘要和折叠计数参与统计；不卡爆索引：`changefeedID`、`dispatcherID`、`regionID`、完整 `error`、原始 `payload` 不能成为默认索引候选 |


### 为什么我们要控制日志数量

日志不是免费的：

- 写盘、格式化、序列化和上下文拼装都有 CPU 和 IO 成本。
- 高频路径和高基数对象会把日志量迅速推高。
- 重复日志会淹没真正重要的信息。
- 大对象和长文本 dump 会拖慢排障，也会抬高存储和检索成本。

因此，日志是运维接口，不是顺手打印的信息。

## 核心原则

### 1. 正常路径静默，异常路径发声

默认不在常规路径上打印过程日志。

保留在默认级别的，应该是少量关键结论，而不是“按执行步骤一路记录走到哪里”的过程轨迹。典型可保留场景包括：

- leader 当选
- changefeed 创建或移除
- maintainer bootstrap 完成
- 组件进入 degraded 或恢复
- 关键配置生效

默认不应保留的日志包括：

- 进入某个函数或分支
- 正常完成某一步
- 高频轮询中的逐次旁白
- 只有 `started`、`finished`、`retrying`、`entered` 一类低语义 message 的日志

#### 避免逐次日志

逐次日志指的是在每一个对象上都会反复打印的日志，对于每个对象只是这个对象自身的一些属性有变化。

打印逐次日志的目的，往往只是为了确认这些对象的工作过程符合预期。在存在海量对象的时候，逐次日志最终可能会造成日志洪流。

* 如果对逐次日志的打印只是为了观察趋势、计数或规模，优先进入 metrics。
* 可以针对反例即不符合预期的情况打印日志，从而减少正常流程上的日志数量。
* 追踪海量对象的工作进度，检测异常对象，周期性打印日志，从而实现定位调查异常情况。

### 2. 用“需要什么动作”决定日志级别

- `ERROR`
  - 正确性、可用性或关键任务进度已受影响，系统无法靠既有恢复逻辑消化，或需要人工关注。
  - changefeed 遇到了会进入 error、failed 等状态的日志。
  - 在错误产生的地方打印该日志，该错误不应该被上层忽略。
- `WARN`
  - 系统还在运行，但进入异常、退化、重试、回退、局部失败状态。必须说明为什么还能继续。
  - 可以自动恢复的非正常状态，比如访问外部的延迟短暂上升等。
- `INFO`
  - 关键生命周期事件、重要状态切换、重要配置揭示、摘要性运行信息。
- `DEBUG`
  - 只在局部排障时有价值的高频细节，但仍然要控制频率、对象大小和语义边界。
  - `DEBUG` 不是“先都打出来，之后再筛”的垃圾桶。应该周期性清理 DEBUG 日志，否则会越来越多，即使打开 DEBUG 级别日志，也不会对排查问题有帮助，反而会迅速膨胀日志，造成更大问题。

#### 思考日志级别

在生产环境中，我们往往只能通过 INFO 级别以上的日志来排查定位问题，DEBUG 级别日志是默认不打印的。

如果调查遇阻，想要打开 DEBUG 级别的日志，这个行为已经是发生在问题出现以后了。

一条日志，如果被设置为了 DEBUG 级别，往往是在暗示它低价值，这样的日志本应该是被删除的。

如果已经有了海量低价值日志，打印频率高，会迅速打印巨量日志，增加了打爆日志服务的风险。

* 如果一条日志，对排查潜在可能问题有价值，那么应该至少打印为 INFO 级别。
* 如果打印一条日志，可能因为规模、程序运行周期等问题，造成海量日志，那么应该使用使用更加机智的方式来打印日志，提供相同的信息。
  * 规模：海量 dispatchers、changefeeds 等。
  * 周期性运行：每个周期打印 checkpoint、resolved-ts 等。

### 3. 默认只保留高价值事件

建议保留在默认级别的日志，主要来自下面几类场景：

- 关键状态切换，如集群 coordinator 切换，节点上下线，changefeed maintainer 切换等等。
- 外部依赖异常，以及系统因此做出的重试、回退、降级、终止决策。
- 用户或运维可感知的重要配置、模式或资源边界变化。
- 明确的 invariant 破坏。

如果一条日志回答不了下面问题中的大部分，它通常不值得保留在默认级别：

- 发生了什么
- 为什么发生
- 影响了谁
- 系统接下来做什么
- 值班同学下一步该看哪里

### 4. 语义放在稳定 `message + 字段` 里

TiCDC 的日志设计要同时对 AI agent 和 Loki 友好，这里约束的是“应用侧日志契约”。

统一要求是：

- `message` 负责稳定摘要，不负责堆砌对象细节。
- 关键语义不能只藏在长 message 里，必须落到结构化字段。

#### Message

`message` 只承担稳定摘要，不承担对象细节堆砌。建议固定采用下面的语义骨架：

- 发生了什么
- 为什么发生
- 系统下一步做什么

推荐写法：

- `campaign coordinator failed due to etcd revision has been compacted, retry later`
- `received drop event from current epoch, reset dispatcher`
- `lock scan found unresolved locks`

不推荐写法：

- `handle handshake event`
- `should not happen`
- `ignore it`
- `failed`

#### 日志字段应该统一，避免使用不同的字段来表达相同的概念

同类对象的字段名必须在全仓长期稳定，不能在不同模块里混用不同口径。

建议统一使用：

- `changefeedID`
- `nodeID`
- `dispatcherID`
- `regionID`
- `subscriptionID`
- `requestID`

避免出现下面这类混用：

- `changefeedID`、`changefeed`、`cf`、`id`
- `nodeID`、`captureID`、`serverID`
- 同一语义在一处叫 `state`，另一处叫 `status`

#### 避免大对象字段

下面这些内容不应出现在默认 `INFO/WARN`：

- 原始 payload
- 完整 event 对象
- 大数组和大对象列表
- 完整 `locks`、`holes`、`slowRegion` 清单
- 自由拼接的长错误链和长文本 dump

如果确实需要，应该改成下面几种方式之一：

- 摘要字段
- 代表样本
- `DEBUG`
- 局部诊断开关或单独排障模式

## 代码评审最小清单

新增、保留或重写一条日志前，至少先过下面这张表：

| 检查项 | 通过标准 | 不通过时优先改成 |
| --- | --- | --- |
| 这是不是默认逐次日志要解决的问题 | 不是单纯的数量、趋势、规模、频率问题 | `metrics`；如果只是担心对象长时间不推进，则补状态记录和异常检测，不要在正常路径持续打印 |
| 它能帮助解决什么问题 | 能回答一个真实排障问题，并说明缺失后排障能力会下降在哪里 | 删除 |
| 它是否与已有日志重复 | 不是同一事件在多层重复表达 | 保留源头日志或边界日志，删掉中间层旁白 |
| 放大 10 倍或 100 倍后会不会刷屏 | 不会随对象数、节点数、轮询次数、重试次数线性膨胀 | state change only、窗口摘要、代表样本、重复折叠、memo + stalled sample |
| 它是否真的有足够的信息量 | 至少能看出对象、原因、动作、影响；stalled/error 还能看出 stage、时长、最近进展、blocker | 补齐字段和语义；不要只写 `failed`、`ignore it`、`started`、`finished` |
| 它是否依赖大对象或长文本 dump | 不依赖完整对象、大数组、长错误链才能表达重点 | 必要字段、摘要字段、代表样本、`DEBUG`、局部诊断开关 |

## 快速否决规则

下面任一情况出现，默认要求修改日志：

- 只是控制流旁白
- 健康路径上的正常事件却按次打印
- 高频重复但没有窗口摘要、重复折叠或 state change only
- 没有稳定对象锚点
- 没有原因、动作或影响
- 大对象直接输出
- 同一错误链路多层重复打印
- 规模放大后会线性刷屏

## 优先采用的治理手段

TiCDC 在治理日志时，默认优先从下面这些手段里选，而不是继续加逐次日志：

- 用 metrics 替代只表达数量、规模、频率和趋势的信息
- 为可能卡住的 workflow 建立追踪，再由独立检测逻辑只在长时间无进展时打印 stalled 日志
- 对周期性路径优先降频，或改成固定时间窗口摘要
- 对同类高频明细优先改成“窗口摘要 + 代表样本”
- 对已稳定、已无诊断价值的正常路径日志直接删除
- 默认不打印大对象，只保留必要字段、摘要字段和代表样本
- 在错误真正发生、最接近根因的位置打印日志
- 谨慎添加 `DEBUG`
