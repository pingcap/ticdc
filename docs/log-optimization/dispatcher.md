# Dispatcher 场景：海量 dispatcher 生命周期日志

## 背景

dispatcher 是 TiCDC 内部数量多、状态变化频繁的一类对象。它的创建、ready、reset、handshake、drop、remove、move 等动作会跨多个模块共同完成，因此默认日志很容易退化成按动作逐条打印的过程旁白。

dispatcher 场景的治理重点是解决如下问题：

- 避免 add dispatcher / remove dispatcher / move dispatcher / reset dispatcher 等场景下产生的海量日志问题。
- 通过日志，可以快速定位问题，哪个 dispatcher 长时间没有进展，卡在了哪个环节。

## 当前存在的问题

### 1. 默认日志围绕离散动作打印，缺少统一状态表达

当前 dispatcher 相关日志更多是在记录单步动作，例如：

- `add dispatcher`
- `commit add dispatcher`
- `send reset dispatcher request to event service`
- `handle handshake event`
- `received a dropEvent, need to reset the dispatcher`
- `remove dispatcher`

这些日志能说明“刚刚发生了一个动作”

### 2. dispatcher 数量一大，默认日志就容易刷屏

dispatcher 是高基数对象。只要对象数量够多，ready、reset、handshake、drop、remove 等动作都会按对象放大日志量。

问题不在于某一条日志单独看有没有价值，而在于：

- 默认日志量会随着对象数和动作数线性增长。
- 同一类问题会被重复打印很多次。
- 真正异常的对象会淹没在大量过程日志里。

### 3. 排障时真正需要的是“谁卡住了”，而不是完整动作流水

值班同学和 AI agent 在排查 dispatcher 问题时，更关心的是：

- 哪些 dispatcher 当前没有推进。
- 它们卡在什么状态。
- 卡了多久。
- 最近一次进展是什么。

也就是说，dispatcher 场景真正需要的是“状态追踪 + 异常检测”，而不是默认保留完整生命周期流水。

## 解决思路

### 1. 用 memo 记录 dispatcher 当前调度状态

对于每个 in-flight dispatcher，不再依赖一串离散日志来表达状态，而是维护一份 memo，记录它当前的调度状态。

这份 memo 至少应能回答下面几个问题：

- 它是谁。
- 当前在执行什么动作。
- 当前处于哪个状态。
- 最近一次进展发生在什么时候。
- 最近一次异常或阻塞信号是什么。

这里的重点不是定义一份很复杂的状态机，而是确保系统内部始终有一个稳定的地方，能表达“这个 dispatcher 现在处于什么状态”。

### 2. 正常推进时只更新 memo，不按步打印默认日志

只要 dispatcher 还在正常推进，就只更新 memo，而不把每次状态变化都打印成默认 `INFO/WARN`。

这样做的结果是：

- 正常路径尽量静默。
- 默认日志不再被 ready、reset、handshake 这类过程动作刷屏。
- 状态仍然保留在系统内部，后续检测和排障都还能使用。

### 3. 通过周期性检测判断 dispatcher 是否卡住

在 memo 之外，增加一层独立的周期性检测逻辑，定期扫描所有 dispatcher：

- 如果一个 dispatcher 在预期时间内持续没有进展，就认为它可能卡住了。
- 只有在这种情况下，才输出少量 stalled 日志。

这样，默认日志表达的就不再是“刚刚做了什么动作”，而是“哪些 dispatcher 现在真的值得关注”。

### 4. 默认日志只保留少量高价值结果

dispatcher 场景的默认日志应收敛为：

- 少量关键结论日志。
- dispatcher stalled 日志。
- 少量真正异常的错误日志。

除此之外的大多数过程信息，都应留在 memo 里，而不是继续作为默认逐次日志输出。

## 为什么这个思路可以解决问题

### 1. 它把“状态记录”和“日志输出”拆开了

当前问题的根源之一，是把“我要知道对象当前状态”这件事，直接等同于“我要不停打日志”。

引入 memo 之后：

- 状态记录继续存在。
- 默认日志只在真正需要提醒人的时候才输出。

这样既不会丢失状态信息，也能显著降低默认日志量。

### 2. 它更符合 dispatcher 场景真正的排障需求

排查 dispatcher 问题时，大家真正关心的不是完整动作流水，而是“有没有卡住”。

用 memo 记录当前状态，再用周期性检测发现长时间无进展的对象，可以直接回答最关键的问题：

- 当前有没有异常 dispatcher。
- 它们卡在什么状态。
- 从什么时候开始卡住。

这比逐条阅读 ready、reset、handshake 日志更接近真实排障方式。

### 3. 它可以从根上缓解海量对象带来的日志洪流

如果继续按动作逐条打印，dispatcher 数量一大，默认日志一定会按对象数线性膨胀。

改成“正常路径只更新 memo，异常路径由周期检测发声”之后：

- 正常对象不会持续占用默认日志。
- 默认日志主要由少量异常对象驱动。
- 对象规模扩大时，日志增长不再直接绑定到每个 dispatcher 的每一步动作。

### 4. 它保留了后续继续细化的空间

这套思路先解决的是方向问题：

- dispatcher 不再按动作打散日志。
- 系统内部先有统一状态记录。
- 默认日志只负责暴露真正值得关注的异常对象。

后续如果需要，再在 memo 字段、卡住阈值、日志聚合方式上继续细化；但在进入这些细节之前，整体方向应该先统一下来。
