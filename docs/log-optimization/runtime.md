# 运行时与基础设施场景

本文主要处理 `ticdc server / cluster` 级别的运行时与基础设施日志，包括启动、关闭、成员变更、后台扫描、重试退避，以及 `Event Service`、`Log Puller`、`Region`、`Subscription` 等公共运行时场景。

## 当前存在的问题

### 1. server / cluster 生命周期旁白过多

启动、关闭和成员变更阶段，默认日志里仍然有很多模块级旁白，例如：

- `closing event dispatcher manager`
- `closed all redo dispatchers`
- `closed all event dispatchers`
- `shared info closed`
- `sink closed`
- `event dispatcher manager closed`

这类日志会把一次 server 或 cluster 级动作拆成很多小步输出，最后形成的问题是：

- 默认日志数量偏多。
- 同一轮启动或关闭过程被切成很多碎片。
- 读者需要自己拼接过程，才能看出整体结果。

### 2. 高频后台路径按次打印，容易刷屏

retry、backoff、polling、后台扫描这类路径运行频率高，默认日志如果继续按次打印，很容易在运行时持续放大。

这类场景的典型问题是：

- 中间重复尝试被反复输出。
- 日志量随时间线性增长。
- 真正需要关注的失败、状态变化和长时间异常被淹没在重复日志里。

### 3. 基础设施问题缺少聚合表达

`slow region`、`holes`、`unresolved locks`、`stale requests` 这类问题往往涉及很多对象。当前如果继续逐对象打印，默认日志会很快失去可读性。

这类场景更常见的问题是：

- 同一种问题会在大量 region 或 subscription 上重复出现。
- 默认日志里堆满对象清单和重复明细。
- 读者很难快速看出影响面、最坏样本和整体趋势。

### 4. 运行时异常场景缺少稳定表达

`ignore`、`drop`、`stale request`、`invariant violation` 这类运行时问题当前缺少稳定表达方式。

在 server / cluster 级排障里，真正需要快速看清的是：

- 哪一类对象受影响。
- 问题和哪个 epoch、版本、请求或 owner 相关。
- 系统已经做了什么处理。
- 当前风险是否还在继续扩大。

## 解决思路

### 1. server / cluster 生命周期收敛为 summary 日志

启动、关闭和成员变更这些 server / cluster 级动作，默认日志应收敛为少量 summary：

- `startup summary`
- `shutdown summary`
- `membership change summary`

summary 日志负责表达：

- 开始动作。
- 关键配置揭示。
- 最终结果。
- 超时、失败或异常细节。

中间模块级旁白应删除，或并入更高层的一条结论日志。

### 2. 高频后台路径改成状态变化和窗口摘要

retry、backoff、polling、后台扫描这类路径，默认日志应重点保留：

- 首次失败。
- 状态变化。
- 固定窗口摘要。
- 最终失败或恢复结果。

中间重复尝试和重复轮询不继续逐条打印。

这部分文档关心的是 server / cluster 级后台行为，例如：

- 某轮后台扫描发现的整体结果。
- 某类重试是否进入新的状态。
- 某个后台流程是否长时间没有推进。

### 3. 基础设施场景使用窗口摘要和样本输出

`Event Service`、`Log Puller`、`Region`、`Subscription` 相关问题，默认日志应优先表达聚合结果，例如：

- 影响对象数量。
- 最老对象年龄。
- 最大 lag。
- 少量代表样本。

完整对象清单和大列表不进入默认 `INFO/WARN`。

### 4. 运行时异常场景统一成少量稳定模板

`ignore`、`drop`、`stale request`、`invariant violation` 这类问题，应统一成少量稳定模板。

每条日志只需要把当前运行时排障真正依赖的信息说清楚：

- 哪一类对象出问题了。
- 当前和哪个 epoch、版本、请求或 owner 相关。
- 系统采取了什么动作。
- 风险是否已经被隔离，还是还会继续影响运行。

### 5. 长时间无进展的场景增加独立检测机制

对于后台扫描、重试退避、运行时状态等待等场景，如果对象或流程长时间没有推进，需要增加独立检测逻辑：

- 正常路径保持收敛。
- 长时间无进展时输出少量异常提示。

这类检测日志负责告诉读者：

- 哪个运行时流程卡住了。
- 卡了多久。
- 当前最值得关注的对象或样本是什么。

## 为什么这个思路可以解决问题

### 1. 它能直接压缩 server / cluster 级默认日志量

启动、关闭、成员变更这些动作本来就属于高层运行时事件。收敛为 summary 之后，默认日志会更短，整体结果也更容易读取。

### 2. 它能控制高频后台路径的长期放大量

高频后台路径的主要问题来自“按次打印”。改成状态变化和窗口摘要后，日志增长速度会明显下降，运行时噪音也会同步降低。

### 3. 它更适合基础设施问题的表达方式

基础设施问题通常关注影响面、趋势和样本。聚合结果比逐对象明细更适合放在默认日志里，也更适合后续检索、聚合和告警。

### 4. 它让运行时异常场景更容易判断影响面

server / cluster 级运行时问题经常需要快速判断“这是局部噪音，还是系统性问题”。统一模板之后，读者更容易直接判断当前风险和后续动作。

### 5. 它保留了对卡住场景的观测能力

日志收敛后，正常路径会更安静。独立检测机制负责在长时间无进展时补充异常提示，这样既能降噪，也能持续发现真正值得关注的问题。
